## The Six SQLite-Backed Durable Objects

All six classes are exported in `worker/cloudflare.config.ts` and `worker/wrangler.toml` with `storage = "sqlite"`:

| Binding | Class | Instance Key | Responsibility |
| --- | --- | --- | --- |
| `DEVICE` | `DeviceGateway` | One per `device_id` | Command queue (`PENDING` → terminal), lease & ack alarms, P-256 nonce replay ledger, WebSocket hibernation, DLQ (`dead_letters` after 5 task attempts) |
| `CHANNEL_CONN` | `ChannelConnection` | `channel:account_id` | Per-account channel dedupe, the 24-hour delivery window, and connector state; one object per account, never one hot object |
| `SCHEDULER` | `Scheduler` | Pinned singleton (`scheduler`) | The paced scheduled queue: due rows, token buckets, quiet hours, and the wake that releases the next send |
| `AUTH_GUARD` | `AuthGuard` | Global singleton | Dual-scope sign-in lockout counters: per-account (5 attempts) and per-IP (20 attempts) within `AUTH_LOCKOUT_WINDOW_SECONDS` (900s) |
| `AUTHORITY_GUARD` | `AuthorityGuard` | Global singleton | Live time-boxed agent authority grant windows and atomic approval race arbitration |
| `ASSISTANT` | `AssistantAgent` | Pinned singleton (`assistant`) | Stateful operator chat (`agents/sessions`), resumable SSE/WS turn streams (`agents/streams`), `tool_calls` fail-closed journal, autonomy enforcement |

> **One-way door**: Adding or renaming a Durable Object class requires matching `exports` in `cloudflare.config.ts` and a full `cf deploy` (never a version-only upload).

## Outbound Delivery: WebSocket + Polling Fallback

1. `POST /v1/sms/send` writes a `PENDING` command into the target handset's `DeviceGateway` Durable Object (deduplicated by optional `idempotency_key`).
2. **Primary path**: If the handset has an open WebSocket (`GET /v1/device/ws`), `DeviceGateway` leases the command (`LEASED`, default `LEASE_MS = 60000`), dispatches it (`DISPATCHED`), and arms an ack timer (`ACK_TIMEOUT_MS = 8000`).
3. **Fallback path**: If the socket is closed, the handset calls `POST /v1/sms/outgoing/poll`, receives leased commands, sends via `SmsSender.kt`, and reports `SENT`, `DELIVERED`, or `FAILED` (`error_code`, `error_message`) via `POST /v1/sms/status/batch`.
4. **Lease expiry & safety**: If a lease expires without acknowledgement, the command returns to `PENDING` (or becomes `EXPIRED` once past its TTL) without duplicating socket dispatch. Never lower `LEASE_MS` below real radio send latency in production.

### Inspecting Live Sockets and Dead Letters

```bash

```

## Multi-Channel Routing (SMS, Telegram, WhatsApp Cloud)

Inbound messages across these three channels normalize into one `conversations` row keyed by `(channel, account_id, peer_id)` and enter the same **Rules (`priority DESC`) → Flows** pipeline:

| Channel | Ingress Endpoint | Verification Header | Outbound Endpoint |
| --- | --- | --- | --- |
| **SMS** | `POST /v1/sms/incoming/batch` | P-256 `X-Signature` | `POST /v1/sms/send` |
| **Telegram** | `POST /v1/channels/telegram/webhook` | `X-Telegram-Bot-Api-Secret-Token` | `POST /v1/channels/telegram/send` |
| **WhatsApp Cloud** | `POST /v1/channels/whatsapp/webhook` (`GET` verify + `POST` ingress) | `X-Hub-Signature-256` | `POST /v1/channels/whatsapp/send` |

The Messenger and Instagram connectors share the same edge pipeline; see [Multi-Channel Connectors](/docs/guides/multi-channel/) for their auth modes and webhook ingress.

> **Current state note**: Both Telegram and WhatsApp inserts currently write `session_state = 'WINDOW_OPEN'`. Automated transitions to `TEMPLATE_ONLY` and `OPTED_OUT` are declared in `0007_multi_platform_and_conversations.sql` but do not yet have background writers (see [State Machines](/docs/reference/state-machines/)).

## Calling DakFlare from Another Cloudflare Worker (`DakFlareApi`)

Another Worker or Cloudflare Workflow in the same account can bind the typed RPC entrypoint `DakFlareApi` instead of constructing raw HTTP requests or bypassing auth via raw DO stubs:

```toml
# consumer wrangler.toml
[[services]]
binding = "DAKFLARE"
service = "dakflare-worker"
entrypoint = "DakFlareApi"
```

`dakflare-worker` is not published to npm, so declare the methods you call rather than importing
a type that cannot be resolved — the guide
[Service binding](/docs/service-binding) has the full
interface, a `WorkflowEntrypoint` example and the retry rule.

```ts
interface DakFlareBinding {
  sendSms(input: { to: string; body: string; idempotencyKey?: string }): Promise<unknown>;
}

export default {
  async fetch(_req: Request, env: { DAKFLARE: Service<DakFlareBinding> }) {
    const sent = await env.DAKFLARE.sendSms({
      to: "+15550169912",
      body: "Payment settled.",
      idempotencyKey: "inv-9021",
    });
    return Response.json(sent);
  },
};
```

Every `DakFlareApi` method (`health`, `deployment`, `devices`, `messages`, `sendSms`, `ask`, `request`) routes through `handleFetch` with `X-Dakflare-Client: binding`, preserving scopes, rate limiters, idempotency, and audit rows. Control authorization via `BINDING_AUTH`:
- `trusted` (default): the Cloudflare account boundary is the credential (refuses with `binding_untrusted` if `ADMIN_TOKEN` is unset).
- `agent_token`: requires a `dkf_agt_` token per call plus live grants for costly scopes.

## Loading a Custom `dakflare.flow/v2` JSON Template via Worker Binding

`DakFlareApi` exposes `request()` as a typed escape hatch to any `/v1/*` route through the exact same auth, rate-limit, and validation pipeline (`worker/src/binding-api.ts`). Use `PUT /v1/admin/workflows/:id` to load or update a custom JSON flow template from another Cloudflare Worker or Cloudflare Workflow:

```ts
/** The part of the `DakFlareApi` binding this task calls; see the service-binding chapter for the complete interface. */
interface DakFlareBinding {
  request(input: {
    path: string;
    method?: string;
    body?: unknown;
    headers?: Record<string, string>;
    token?: string;
  }): Promise<{ status: number; body: unknown; bookmark: string | null }>;
  sendSms(
    input: { to: string; body: string; deviceId?: string; idempotencyKey?: string },
    options?: { token?: string }
  ): Promise<unknown>;
}

interface Env {
  DAKFLARE: Service<DakFlareBinding>;
  DAKFLARE_AGENT_TOKEN?: string; // only needed if BINDING_AUTH=agent_token
}

const customTemplate = {
  name: "Invoice OTP & Receipt Handler",
  enabled: true,
  device_id: "dev63f3953f417d587f",
  graph: {
    schema: "dakflare.flow/v2",
    nodes: [
      { id: "t1", type: "trigger", data: { kind: "incoming", body: { mode: "keyword", value: "INV-" } } },
      { id: "x1", type: "extract", data: { source: "body", pattern: "INV-(?<invoice>[0-9]{6})" } },
      { id: "s1", type: "send_sms", data: { to: "{{sender}}", body: "Invoice {{invoice}} logged." } },
      { id: "e1", type: "stop", data: {} },
    ],
    edges: [
      { id: "e1", source: "t1", target: "x1" },
      { id: "e2", source: "x1", target: "s1" },
      { id: "e3", source: "s1", target: "e1" },
    ],
  },
};

export default {
  async fetch(_req: Request, env: Env): Promise<Response> {
    try {
      // 1. Load & validate the custom JSON template (Worker computes rank-v1 layout automatically)
      const saved = await env.DAKFLARE.request({
        path: "/v1/admin/workflows/wf_invoice_custom",
        method: "PUT",
        body: customTemplate,
        ...(env.DAKFLARE_AGENT_TOKEN ? { token: env.DAKFLARE_AGENT_TOKEN } : {}),
      });

      // 2. Or send an outbound SMS directly from a Cloudflare Workflow / Worker
      const sent = await env.DAKFLARE.sendSms({
        deviceId: "dev63f3953f417d587f",
        to: "+15550142299",
        body: "Custom template deployed.",
        idempotencyKey: "deploy-wf-invoice-custom",
      });

      return Response.json({ saved: saved.body, sent });
    } catch (err) {
      // A refusal is a thrown error carrying a stable `code`; branch on it, not the sentence.
      if (err instanceof Error && "code" in err) {
        const failure = err as Error & { code?: string; status?: number };
        return Response.json(
          { error: failure.code, message: failure.message },
          { status: failure.status ?? 400 }
        );
      }
      throw err;
    }
  },
};
```

> **Execution model note**: `dakflare.flow/v2` workflows are event-driven (`trigger.data.kind === "incoming"`): once saved via `PUT /v1/admin/workflows/:id`, the workflow syncs to the handset (`GET /v1/flows`) and runs automatically on matching inbound SMS/Telegram/WhatsApp messages. There is no ad-hoc `POST /v1/workflows/:id/run` endpoint in `worker/src/index.ts`; for imperative outbound dispatch from another Worker, call `env.DAKFLARE.sendSms(...)` or `env.DAKFLARE.request({ path: "/v1/channels/telegram/send", method: "POST", body: ... })`.
