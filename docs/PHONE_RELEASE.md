# Phone release build

Status: `0.2.0` (versionCode 200) is the first signed, non-debuggable APK.
It is built for sideloading; it is **not** published on Google Play or F-Droid
and there is deliberately no `metadata/` directory yet (see
[F-Droid readiness](#f-droid-readiness)).

The app is the SMS gateway. The console, worker and protocol are separate; this
page only covers the Android artefact in `simulator/src-tauri/gen/android/`.

## Build

```sh
simulator/scripts/release-apk.sh
```

The script sources `~/.config/dakflare/android-env.sh` (written by
`simulator/scripts/android-setup.sh`), requires the signing key, runs
`npx tauri android build --apk --target aarch64`, and prints the APK path, size,
`apksigner verify --print-certs` output and the version. It refuses to run when
the keystore is missing.

Output:

```
simulator/src-tauri/gen/android/app/build/outputs/apk/universal/release/app-universal-release.apk
```

(`universal` is the Gradle flavour name; the APK is arm64-v8a only — verified
with `unzip -l`.)

Manual equivalent, if the script is in the way:

```sh
source ~/.config/dakflare/android-env.sh
cd simulator
npx tauri android build --apk --target aarch64
```

Gradle independently refuses a release build without a key: the
`verifyReleaseSigning` task fails before packaging and never falls back to the
debug key. It also prints the certificate fingerprint into the build output.

| Credentials | `~/.config/dakflare/release-keystore.txt` (mode 600: `alias`, `storePassword`, `keyPassword`) |
| Alias | `dakflare` |

| Certificate SHA-256 | `77:B2:81:84:75:8F:82:9E:93:53:C2:6C:44:0F:06:BB:28:5D:9C:83:D1:1F:99:F1:89:67:39:25:1F:DC:81:F6` |
| APK cert digest (`apksigner`) | `77b28184758f829e9353c26c440f06bb285d9c83d11f99f1896739251fdc81f6` |

Neither file is in the repository; `*.jks` and `*.keystore` are ignored under
`gen/android/` as a second line of defence.

The build reads, in order, the environment and then the config file:

```
DAKFLARE_KEYSTORE           path to the .jks
DAKFLARE_KEYSTORE_PASSWORD  store password
DAKFLARE_KEY_ALIAS          key alias (default: dakflare)
DAKFLARE_KEY_PASSWORD       optional; PKCS#12 shares the store password
```

To recreate the key (only if it is truly gone — see below):

```sh
keytool -genkeypair -keystore ~/.config/dakflare/dakflare-release.jks \
  -storetype PKCS12 -alias dakflare -keyalg RSA -keysize 4096 \
  -validity 10000 -dname "CN=DakFlare Release, OU=Android, O=DakFlare, L=Dhaka, C=BD"
```

### Losing the key means losing upgrades

Android only replaces an installed app in place when the new APK carries the
same signing certificate. With this key gone:

- every installed copy must be uninstalled before a new build installs, and
  uninstalling deletes the paired identity and the message store;
- the SMS role is released and must be granted again, and the phone re-paired
  with the backend;
- F-Droid treats it as a different package signer, so a future listing would
  need a new application id (or the key archived by F-Droid, which this project
  is not doing).

Keep an offline copy. Do not rotate the key for convenience.

## Version scheme

One source: `simulator/src-tauri/tauri.conf.json`

```json
"version": "0.2.0",
"bundle": { "android": { "versionCode": 200 } }
```

`app/build.gradle.kts` reads exactly these two fields; `app/tauri.properties` is
generated by the Tauri CLI (it mirrors the same values) but is **not** read by
the build, so the two can never disagree silently.

- `version` is the user-visible name; bump it for a release.
- `bundle.android.versionCode` must strictly increase for every artefact that
  will be installed over an older one. It is intentionally not derived from the
  version name (the Tauri default would be `major*1000000 + minor*1000 + patch`).

Transition note: the pre-0.2.0 debug build reported versionCode 1000 (Tauri's
derived value) while 0.2.0 is 200. A handset still holding that build treats 200
as a downgrade even with the same key, so it needs `adb install -r -d` for a
same-key debug reinstall, and an uninstall before a release install. This is the
one place where the version code had to move backwards; every later release must
only increase.

## Install

```sh
adb install -r simulator/src-tauri/gen/android/app/build/outputs/apk/universal/release/app-universal-release.apk
```

- Same certificate and a higher versionCode: `-r` keeps data.
- Debug build → release build: `INSTALL_FAILED_UPDATE_INCOMPATIBLE` (different
  certificates). Android has no way to keep the data; uninstall first and expect
  to re-pair and re-grant the SMS role. Do not uninstall a handset you cannot
  re-pair.
- The release APK is `debuggable=false`, so `run-as` does not work on it.
  `simulator/scripts/device-check.sh` pulls `simulator.db` with `run-as` and uses
  the WebView devtools socket, so the full 8/8 run needs the **debug** build.
  On a release build only `attached` and `role` (and dumpsys/logcat
  observations) work.
- Debug rebuilds from this tree also carry versionCode 200. Against a handset
  still holding the old 1000 debug build, a same-key debug reinstall needs
  `adb install -r -d`; this is a local-debug detail, not a release path.

## Permissions and the SMS role

Every permission in the release manifest, and why:

| Permission | Why |
|---|---|
| `INTERNET` | Pairing and message sync with the self-hosted backend over HTTPS. |
| `RECEIVE_SMS` | Inbound SMS to the gateway even with no Activity running. |
| `SEND_SMS` | Flow replies and user sends from the composer. |
| `READ_PHONE_NUMBERS` | Own-number sources for the self-number guard; without it the guard reports "unknown". |
| `READ_PHONE_STATE` | Subscription/SIM list for routing a send to the right slot. Normal permission, granted at install. |
| `POST_NOTIFICATIONS` | Inbound-message notification and the foreground-service notification. Runtime request on Android 13+. |
| `FOREGROUND_SERVICE` | The gateway drain is a foreground service. |
| `FOREGROUND_SERVICE_REMOTE_MESSAGING` | The platform's category for that service; also one Android 15 allows to start from boot. |
| `RECEIVE_BOOT_COMPLETED` | Restart the gateway after a reboot, only when a paired identity exists. |

There is no contacts, storage, location, camera or microphone permission.

Default-SMS role requirements are all declared, because Android will not offer
the role without them:

- `MainActivity` handles `SENDTO`/`VIEW` for `sms:`, `smsto:`, `mms:`, `mmsto:`;
- `SmsReceiver` handles `SMS_DELIVER` (and `SMS_RECEIVED`, so the gateway keeps
  working when another app holds the role);
- `RespondViaMessageService` answers `RESPOND_VIA_MESSAGE` (protected by
  `SEND_RESPOND_VIA_MESSAGE`) — a deliberate no-op required for eligibility;
- `MmsReceiver` accepts `WAP_PUSH_DELIVER` and drops the push; the role requires
  the receiver even though MMS is out of scope.

The role is requested at runtime through `RoleManager`; it is never assumed.

## Network policy

Release builds set `android:usesCleartextTraffic="false"`; debug overrides it to
`true` only so the WebView can reach the Vite dev server at
`http://localhost:1420`. The core accepts an `http://` base URL, but on a release
build Android blocks cleartext, so the shipped app is HTTPS-only in practice.
Pairing stores `https://…workers.dev`-style worker URLs.

## F-Droid readiness

Not submitted. When it is, F-Droid reviewers will ask:

1. **SMS permissions and the default-SMS role.** SMS apps are allowed, but the
   app must actually be a default SMS handler — here the role is also what makes
   the gateway work. Google Play's SMS policy is a separate reason this is
   sideload/F-Droid only.
2. **`NonFreeNet` / remote backend.** The app is useless without a backend for
   pairing, and the supported backend is a Cloudflare Worker. The worker source
   is in `worker/` and the URL is configured per install (no instance is
   hardcoded), so the honest position is "self-hosted free software, third-party
   hosting required". A reviewer may still apply `NonFreeNet` to the hosting
   dependency. There is no analytics, telemetry, ad SDK, Firebase or Google Play
   Services; `Tracking` should not apply.
3. **Reproducible builds.** Rust + NDK + npm/Cargo dependencies make a
   bit-for-bit match hard. Expect a recipe request, and possibly a
   non-reproducible build accepted only with the upstream signature.
4. **Build metadata.** F-Droid needs a recipe in `fdroiddata` and fastlane
   metadata. Writing `metadata/` before an actual submission would be noise:
   the app still needs a backend to pair, MMS is unsupported, and the signing
   history is only just established. Add it at submission time, together with
   the exact version/versionCode the tag builds.

## Known gaps

- **MMS is unsupported.** `MmsReceiver` exists solely so the SMS role can be
  granted; a WAP push is dropped, not downloaded.
- **A backend is required to pair.** A fresh install with no worker URL cannot
  send or receive through DakFlare; SMS still arrives at the phone.
- **No in-place upgrade from the debug build** (certificate change, and
  versionCode 200 < 1000). Uninstall loses the paired identity and messages.
- **`run-as` unavailable** on the release APK, so the database checks in
  `simulator/scripts/device-check.sh` only run against a debug build.
- **Not on Play.** SMS permissions plus the default-SMS role put it outside
  Play's default policy.

## Verifying a build

```sh
apksigner verify --verbose --print-certs <apk>
aapt2 dump badging <apk> | head -1
```

Expected: `versionCode='200' versionName='0.2.0'`, no `application-debuggable`
line, certificate SHA-256 digest
`77b28184758f829e9353c26c440f06bb285d9c83d11f99f1896739251fdc81f6`, and the
permissions above plus the SMS role components.
